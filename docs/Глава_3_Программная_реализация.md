# Глава 3. ПРОГРАММНАЯ РЕАЛИЗАЦИЯ

В этой главе описывается практическая реализация официального сайта Оршанского колледжа – филиала УО «БелГУТ» (ogkjt.bsut.by) на выбранном стеке: серверная часть системы управления контентом на Strapi 5 и клиентская часть приложения на Next.js 15 с TypeScript и Tailwind CSS. По сути здесь изложено то, как спроектированные в главе 2 решения были перенесены в код, как настраивалось окружение и как система выводилась в эксплуатацию на VDS. Объём работ получился немалый: от инициализации проектов до настройки swap-файла из-за нехватки памяти при сборке Strapi и ручной проверки вёрстки на разных устройствах. Ниже по подразделам — архитектура, бэкенд, фронтенд, динамическое меню, версия для слабовидящих, тестирование и деплой.

## 3.1 Общая архитектура решения

Архитектура реализованного сайта строится на разделении двух частей: серверная часть системы управления контентом отвечает за хранение и выдачу контента через API, клиентская часть приложения — за отображение страниц пользователю и серверный рендеринг. Такой подход был обоснован в главе 1 и спроектирован в главе 2; в реализации он воплощён в виде двух отдельных приложений, которые общаются по HTTP через REST API Strapi. На самом деле это не просто «два сервиса», а сознательное разделение зон ответственности: контент меняется в одном месте, а то, как он выглядит и по каким адресам отдаётся, живёт в другом. Так проще поддерживать сайт без постоянного вмешательства программиста в код при каждом обновлении новости или пункта меню.

Серверная часть системы управления контентом развёрнута на базе Strapi 5 [8]. Strapi работает как отдельный Node.js-процесс: в нём описаны типы контента (коллекции article, event, page и единичные типы global и homepage), компоненты для меню и блоков главной страницы, встроенная админ-панель для редакторов. Данные хранятся в SQLite в режиме разработки; для production в проекте предусмотрена возможность переключения на PostgreSQL. API отдаёт JSON по маршрутам вида /api/articles, /api/events, /api/pages, /api/global и т.д. Клиентская часть не генерирует контент сама — она только запрашивает его у Strapi и рендерит в HTML. В принципе это и есть классическая схема Headless CMS: один источник правды для контента, один — для представления. Документация Strapi [8] подробно описывает REST API и форматы ответов; при реализации типы ответов были перенесены в TypeScript-интерфейсы на стороне Next.js, чтобы сохранять типобезопасность при работе с данными.

Клиентская часть приложения реализована на Next.js 15 [9, 10] с использованием App Router, React и TypeScript. Next.js выполняет серверный рендеринг: при запросе страницы данные из Strapi подтягиваются на сервере, HTML собирается и отдаётся браузеру уже готовым. Это даёт быструю первую отрисовку и удобство для поисковой индексации. Сборка фронтенда выполняется командой npm run build; итоговое приложение запускается в режиме Node.js (next start) и обслуживает запросы на заданном порту. Развёртывание в данном проекте выполнено без контейнеризации: оба приложения (Strapi и Next.js) работают на одном VDS под управлением менеджера процессов. Обратный прокси (Nginx) принимает входящие запросы, по домену или пути направляет их на нужный порт и при необходимости отдаёт статику. SSL для домена ogkjt.bsut.by настраивался отдельно; если честно, с сертификатами пришлось повозиться из-за особенностей панели хостинга, но в итоге HTTPS работает. Контейнеризация (Docker) в задании не предусматривалась, поэтому развёртывание делалось «голым» Node.js и Nginx — проще с точки зрения отладки и обновлений на небольшом сервере.

Выбор именно такой схемы (два процесса, один VDS, без контейнеров) обусловлен ограничениями по ресурсам и задачей колледжа: сайт должен стабильно работать при типичной посещаемости, при этом бюджет на хостинг не бесконечный. Один сервер с 2 ГБ ОЗУ и двумя ядрами в итоге оказался достаточным после решения проблемы со сборкой Strapi (об этом в подразделе 3.7). Ниже приведена упрощённая схема взаимодействия компонентов: пользователь обращается к сайту по домену; Nginx перенаправляет запрос на экземпляр Next.js; Next.js по внутреннему запросу обращается к API Strapi, получает данные и формирует HTML; статика и медиа могут отдаваться напрямую или через тот же прокси.

## 3.2 Серверная часть системы управления контентом (Strapi)

Серверная часть системы управления контентом реализована на Strapi 5. Проект инициализирован в каталоге backend корневого репозитория; зависимости устанавливаются через npm, конфигурация окружения выносится в .env (URL приложения, порт, настройки БД, ключи для админки и API). В документации Strapi [8] описаны структура проекта, Content-Type Builder и работа с компонентами; при реализации опирались именно на неё, плюс на спроектированную в главе 2 модель данных. Инициализация нового проекта Strapi выполняется стандартной командой; после этого в папке src/api добавляются каталоги для каждого типа контента (article, event, page, global), внутри — content-types с JSON-схемами, контроллеры, сервисы и маршруты. Компоненты (например, menu-section и menu-link для меню) лежат в src/components/elements и подключаются к атрибутам типов через указание component в схеме. Так получилось, что сначала были описаны коллекции, потом единичные типы и компоненты, затем проверена работа API через браузер или Postman — и только после этого клиентская часть начала забирать данные.

Типы контента реализованы в виде коллекций и единичных типов. Коллекция article (новости) содержит поля title, slug (UID от title), announcement, content (Blocks), cover (Media, images), date; включён режим draft and publish, чтобы редактор мог готовить материалы и публиковать их отдельным действием. Коллекция event (мероприятия) включает title, date (DateTime), location, description (Blocks), при необходимости file (Media). Коллекция page (статические страницы) — title, slug, content (Blocks). Все три коллекции используются для наполнения разделов сайта: новости выводятся на главной и на странице списка новостей, события — в блоке календаря и на отдельной странице мероприятия, страницы — для разделов «О колледже», «Абитуриентам», «Одно окно» и т.д. Схема одной из моделей (article) в формате Strapi приведена в листинге 3.2.1.

*Листинг 3.2.1 — Фрагмент схемы коллекции article (backend)*

```json
{
  "kind": "collectionType",
  "collectionName": "articles",
  "info": {
    "singularName": "article",
    "pluralName": "articles",
    "displayName": "News",
    "description": "Новости колледжа"
  },
  "options": { "draftAndPublish": true },
  "attributes": {
    "title": { "type": "string", "required": true },
    "slug": { "type": "uid", "targetField": "title" },
    "announcement": { "type": "text", "required": true },
    "content": { "type": "blocks" },
    "cover": { "type": "media", "multiple": false, "allowedTypes": ["images"] },
    "date": { "type": "date" }
  }
}
```

Единичный тип global хранит глобальные настройки: главное меню в виде повторяемого компонента (menu-section с полями title, url и вложенным массивом links — menu-link с title и url), контакты (address, phoneReception, phoneDirector, email), ссылки на соцсети (instagramLink, telegramLink, tiktokLink). Единичный тип homepage спроектирован для настроек главной страницы: Hero-блок (заголовок, подзаголовок, текст, фоновое изображение, повторяемые кнопки/ссылки), панель быстрого доступа (повторяемый компонент с названием, ключом иконки, ссылкой, цветом), блок «Полезная информация» (заголовок и карточки с названием, описанием, ссылкой, цветом), блок официальных сайтов (заголовок и список ссылок). Иконки в панели быстрого доступа задаются через enum с предопределёнными ключами; в клиентской части ключу ставится в соответствие компонент иконки (например, из набора Lucide), так что менять подписи и ссылки можно в Strapi без правок кода. Контроллеры, сервисы и маршруты для article, event, page и global использованы стандартные, сгенерированные Strapi; кастомной бизнес-логики в первой версии не добавлялось. Права доступа настроены так: для анонимных запросов разрешены find и findOne по публичным типам контента, доступ к админ-панели и на изменение данных имеют только авторизованные пользователи с ролями Editor или Administrator. Настройка прав в Strapi выполняется через раздел Settings — Users & Permissions — Roles: для роли Public включаются только нужные эндпоинты на чтение, для Authenticated при необходимости добавляются роли Editor и Administrator с расширенными правами. Медиафайлы (обложки новостей, вложения событий) отдаются через тот же API с populate; URL картинок в ответе могут быть относительными, поэтому на клиенте используется функция сбора полного URL (getStrapiURL() или аналог), чтобы изображения корректно подгружались при развёртывании на домене ogkjt.bsut.by. По итогу имеем следующее: серверная часть полностью берёт на себя хранение и выдачу контента, админ-панель доступна по защищённому URL, публичное API не раскрывает служебных данных и достаточно для работы клиентской части.

**Вывод по подразделу 3.2.** Серверная часть системы управления контентом реализована на Strapi 5: коллекции article, event, page и единичные типы global, homepage с компонентами меню и блоков главной страницы. Контент управляется через админ-панель; публичное API отдаёт данные для клиентской части. Роли и права соответствуют спроектированной модели (глава 2).

## 3.3 Клиентская часть приложения (Next.js)

Клиентская часть приложения реализована на Next.js 15 с App Router [9, 10]. Структура маршрутов повторяет спроектированную информационную архитектуру: корневая страница (главная), разделы about (О колледже с подразделами administration, contacts, corruption, history, services, symbols), applicants (Абитуриентам с specialties, plan, documents, transfer), students (Обучающимся с day, correspondence, dormitory), ideology (Воспитательная работа с spps, youth-policy, curator), one-window, appeals, news (список и страница новости по slug), events (страница события по id). Общие layout (шапка и подвал) вынесены в корневой layout.tsx; шапка и подвал загружают данные из Strapi (глобальные настройки, меню, контакты, блок официальных сайтов) и передают их в клиентские компоненты. Так получилось, что часть компонентов остаётся серверной (например, обёртки, которые делают fetch к API), а часть — клиентской (интерактивное меню, кнопки, панель быстрого доступа), что соответствует рекомендациям Next.js по использованию Server и Client Components.

Интеграция с API Strapi вынесена в модуль strapi.ts в каталоге lib. В нём определены типы (Article, Event, Page, GlobalSettings, MenuSection, MenuLink и др.) и функции getGlobalSettings(), getArticles(), getArticleBySlug(), getEvents(), getEventById(), getPageBySlug(). Запросы выполняются через fetch с базовым URL из конфигурации (getStrapiURL()); для списков используется пагинация и при необходимости revalidate или cache: "no-store". Данные для главной страницы (Hero, панель быстрого доступа, блок полезной информации, блок официальных сайтов) при наличии типа homepage в Strapi могут подгружаться отдельной функцией и подставляться в соответствующие блоки; в текущей реализации Hero и быстрые ссылки могут быть частично захардкожены или браться из Strapi в зависимости от готовности Single Type homepage. Главное — что точка входа для всех данных API сосредоточена в одном модуле, типизация единая, и при добавлении новых полей в Strapi достаточно расширить интерфейсы и вызовы.

Интерфейсные блоки реализованы компонентами в папке components: blocks (Hero, NewsGrid, Events, QuickAccessPanel, QuickLinks, Features), layout (Header, Footer, Logo). Hero отображает первый экран с фоновым изображением, заголовком, подзаголовком и кнопками; при наличии данных из Strapi они подставляются вместо статичного текста. Панель быстрого доступа (QuickAccessPanel) выводит набор иконок-ссылок (расписание, одно окно, версия для слабовидящих и т.д.); элементы и ссылки при наличии homepage приходят из API. Блок «Полезная информация» (QuickLinks) и блок официальных сайтов в подвале строятся по тому же принципу: данные из Strapi, разметка и стили в React и Tailwind. Адаптивная вёрстка выполнена на Tailwind CSS [11]: используются breakpoints (sm, md, lg, xl), утилитарные классы для отступов, размеров шрифта и сеток; на малых экранах меню сворачивается в выдвижную панель (Sheet), контент перестраивается в одну-две колонки. Формы обратной связи в проекте не реализованы, как и было заложено в требованиях. Документация Next.js [9, 10] по App Router и серверным компонентам использовалась при выносе загрузки данных в серверные обёртки (например, HeaderWrapper, FooterWrapper), чтобы не тянуть лишний JavaScript на клиент и при этом сохранять интерактивность там, где она нужна — в меню, кнопках и панели быстрого доступа. Цветовая палитра и переменные темы (светлая/тёмная) заданы в globals.css через CSS-переменные и класс .dark на корне; компоненты Shadcn UI [12] из коробки подхватывают эти переменные, поэтому единообразие интерфейса сохраняется без дублирования стилей в каждом блоке.

## 3.4 Динамическое меню

Главное меню сайта формируется динамически из данных серверной части системы управления контентом. В Strapi структура меню описана в единичном типе global: поле mainMenu — повторяемый компонент elements.menu-section, каждый элемент которого содержит title, url и массив links (компонент elements.menu-link с title и url). Таким образом поддерживается двухуровневое меню: разделы верхнего уровня с подпунктами. Редактор или администратор в админ-панели может добавлять и удалять пункты, менять названия и ссылки; привязка может вести на внутренние страницы (slug из коллекции page) или на внешние URL. Реализация в Strapi выполнена через Content-Type Builder и JSON-схемы компонентов; при необходимости структуру можно расширить третьим уровнем или дополнительными полями.

В клиентской части приложения меню загружается при рендеринге layout. Обёртка HeaderWrapper (серверный компонент) вызывает getGlobalSettings(), из ответа извлекается mainMenu и передаётся в компонент Header как initialMenu. Header — клиентский компонент: он принимает initialMenu и отображает навигацию в виде NavigationMenu (Shadcn UI) на десктопе и выдвижной панели (Sheet) на мобильных. Пункты с подпунктами рендерятся как выпадающие блоки с ссылками; пункты без подпунктов — как обычные ссылки. Если по какой-то причине API недоступен или mainMenu пустой, используется запасной вариант (defaultMenu) с предзаданной структурой разделов, чтобы сайт оставался работоспособным. Активный пункт меню при необходимости подсвечивается по текущему pathname; для доступности используются семантическая разметка, ARIA-атрибуты и навигация с клавиатуры в соответствии с возможностями Shadcn UI [12]. В принципе передача меню «сверху вниз» от серверного компонента к клиентскому решает проблему гидрации: на сервере уже есть актуальный список пунктов, клиент не делает повторный запрос при первом рендере и просто отображает переданные данные. Добавление или переименование раздела в Strapi после публикации сразу отражается на сайте при следующей загрузке страницы или по истечении revalidate, если используется кеширование. Так что динамическое меню в реализации действительно динамическое — без правок кода фронтенда.

*Листинг 3.4.1 — Пример загрузки меню в layout и передачи в Header*

```tsx
// HeaderWrapper.tsx (серверный компонент)
import { getGlobalSettings } from "@/lib/strapi";
import { Header } from "./Header";

export async function HeaderWrapper() {
  const globalSettings = await getGlobalSettings();
  const menu = globalSettings?.mainMenu || null;
  return <Header initialMenu={menu} />;
}
```

**Вывод по подразделу 3.4.** Динамическое меню реализовано через тип global в Strapi (mainMenu, компоненты menu-section и menu-link) и загрузку этих данных в layout клиентской части. Header строит навигационное дерево из переданного массива; на десктопе используется NavigationMenu, на мобильных — выдвижная панель. Изменение состава и названий пунктов меню выполняется в админ-панели без правок кода фронтенда.

## 3.5 Версия для слабовидящих

Требования к доступности для инвалидов по зрению заданы СТБ 2105-2010 [5] и WCAG 2.1 [6]. В реализованной системе предусмотрен режим «Версия для слабовидящих»: контрастная тема и управление размером шрифта с сохранением выбора пользователя между сессиями. Реализация выполнена на стороне клиентской части приложения без изменений в Strapi.

В шапке сайта размещён переключатель «Версия для слабовидящих» (иконка и подпись). При нажатии клиентская часть переключает интерфейс в режим с повышенной контрастностью и увеличенным базовым размером шрифта. Цвета задаются через CSS-переменные: в режиме для слабовидящих переопределяются переменные фона и текста так, чтобы обеспечить контраст не ниже требований WCAG 2.1 уровня AA (для крупного текста и интерфейсных элементов). Размер шрифта увеличивается относительно базового (например, с 16px до 18–20px или на 20–25%); при необходимости отключаются или упрощаются фоновые изображения в Hero и других блоках, чтобы не отвлекать и не снижать читаемость. Анимации при включённом режиме можно отключить или ослабить через медиа-запрос prefers-reduced-motion или отдельный класс на корневом элементе.

Состояние режима (включён или выключен) сохраняется в localStorage под выбранным ключом (например, a11y-low-vision или theme-low-vision). При загрузке страницы клиентский скрипт читает это значение и применяет к корневому элементу (html или body) соответствующий класс или атрибут (например, data-a11y="low-vision" или class="a11y-low-vision"). Стили для этого состояния прописаны в глобальном CSS (globals.css) или в Tailwind: переопределение --background, --foreground, размера шрифта и при необходимости скрытие фоновых изображений. Таким образом пользователю не нужно включать режим при каждом визите — выбор сохраняется. Переключатель доступен с клавиатуры и имеет понятную подпись для скринридеров (aria-label или видимый текст). Реализация специально не использует cookie для этого выбора: localStorage проще с точки зрения кода на клиенте и не создаёт лишних запросов с заголовками cookie; срок хранения не критичен, пользователь при необходимости может сбросить режим повторным нажатием. Соответствие СТБ 2105-2010 [5] и WCAG 2.1 [6] по контрасту и масштабированию текста в данной реализации достигается за счёт описанного набора мер; при дальнейшей доработке можно добавить отдельные уровни увеличения шрифта (например, два шага: «увеличить» и «максимум») или дополнительные настройки, сохраняя их там же в localStorage.

## 3.6 Тестирование

Тестирование реализованного сайта проводилось вручную. Автоматизированные тесты (unit, e2e, нагрузочные) в рамках дипломного проекта не разрабатывались; проверялись корректность отображения контента, работа навигации и меню, адаптивность вёрстки на разных устройствах и разрешениях, а также режим для слабовидящих.

Проверка вёрстки выполнялась на реальных устройствах и экранах: iPhone 16, смартфон Xiaomi Redmi Note 14 Pro 5G, мониторы с разрешениями 2K и Full HD. Цель — убедиться, что страницы не «ломаются» на малых и больших ширинах, меню открывается и закрывается, текст читаем, кнопки и ссылки доступны. На разных разрешениях периодически проявлялись мелкие баги отображения, связанные с Tailwind: например, отступы или переносы блоков на границах breakpoints (md, lg), когда один и тот же класс вёл себя по-разному из-за медиа-запросов. Такие случаи фиксились точечными правками: уточнение классов (gap, padding, max-width), добавление или снятие условных отображений (hidden/block на определённых breakpoints), проверка контейнеров и flex/grid. По итогу имеем следующее: вёрстка ведёт себя стабильно на указанных устройствах; на очень малых ширинах (узкие телефоны) при необходимости подправлялись размеры шрифтов и кнопок, чтобы элементы не наезжали друг на друга.

Функциональная проверка включала просмотр главной страницы, переходы по разделам и подразделам, открытие новостей и событий, отображение статических страниц. Проверялась работа динамического меню: загрузка из Strapi, отображение подпунктов, переход по ссылкам. Режим для слабовидящих включался и выключался; проверялось сохранение состояния после перезагрузки страницы и смена контраста и размера шрифта. Контент в админ-панели Strapi создавался и редактировался (CRUD для новостей, событий, страниц, настройки global и при наличии homepage); после публикации изменения проверялись на сайте. Нагрузочное тестирование и автоматизированные сценарии не проводились; оценка производительности ограничена субъективным восприятием скорости загрузки страниц при обычном использовании. То есть ни нагрузочных тестов самого сайта, ни автоматизированных e2e или unit-тестов в рамках диплома не делалось — только ручная проверка по сценариям «зашёл на главную, прошёлся по разделам, открыл новость, проверил меню и режим для слабовидящих». Для сайта учреждения образования с ожидаемой посещаемостью в пределах тысяч просмотров в день такой подход считался достаточным; при необходимости в будущем можно добавить автоматические тесты и замеры производительности отдельным этапом развития проекта.

## 3.7 Деплой и настройка окружения (в том числе swap при сборке Strapi)

Развёртывание сайта выполнено на виртуальном выделенном сервере (VDS) у провайдера hoster.by. Конфигурация сервера: 2 ГБ оперативной памяти (ОЗУ) и 2 ядра процессора. На этом же сервере запущены оба приложения — серверная часть системы управления контентом (Strapi) и клиентская часть (Next.js), а также обратный прокси Nginx для приёма входящих запросов по домену ogkjt.bsut.by и перенаправления на соответствующие порты. SSL-сертификат для HTTPS настраивался через панель хостинга или вручную (Let's Encrypt); настройка заняла дополнительное время из-за особенностей панели и привязки домена, но в итоге доступ по HTTPS работает.

Сборка приложений выполнялась непосредственно на сервере. Клиентская часть (Next.js) собирается командой npm run build; процесс в условиях 2 ГБ ОЗУ обычно завершается успешно. Сборка серверной части (Strapi) командой npm run build оказалась проблемной. Strapi при сборке потребляет значительный объём оперативной памяти: компиляция админ-панели и подготовка production-сборки приводят к пиковой нагрузке на RAM. На конфигурации с 2 ГБ ОЗУ сборка Strapi завершалась с ошибкой из-за нехватки памяти (OOM — Out of Memory): процесс убивался ядром или менеджером процессов, в логах фиксировалась ошибка типа JavaScript heap out of memory или Kill signal. Это важный этап настройки окружения, с которым пришлось разбираться отдельно.

Принятое решение — создание на сервере swap-файла (файла подкачки). Swap позволяет использовать часть дискового пространства как виртуальную память: когда физической RAM не хватает, ядро сбрасывает редко используемые страницы памяти на диск и при необходимости подгружает их обратно. Для сборки Strapi этого достаточно, так как пиковая потребность во времени сборки кратковременна. На сервере был создан swap-файл размером 2–4 ГБ (конкретное значение выбиралось с учётом свободного места на диске и рекомендаций по размеру порядка половины или равного объёму RAM). Команды выполнялись вручную или через скрипт: создание файла (dd или fallocate), назначение прав, подключение через mkswap и swapon, при необходимости добавление записи в fstab для сохранения после перезагрузки. После включения swap сборка Strapi (npm run build в каталоге backend) успешно завершилась; сборка Next.js также прошла без ошибок. В эксплуатации при типичной нагрузке сайта колледжа 2 ГБ ОЗУ оказывается достаточно: оба процесса работают, swap используется в основном при пиковых запросах или фоновых задачах. Рекомендация при аналогичном развёртывании: на VDS с 2 ГБ RAM заранее планировать наличие swap 2–4 ГБ для этапа сборки Strapi. Долгий билд Strapi — известная особенность: админ-панель собирается как отдельное приложение (React), плюс бандлинг и оптимизация, и в момент пика потребление памяти легко переваливает за 2 ГБ. Без swap процесс обречён на OOM; с swap сборка идёт дольше по времени (из-за подкачки), но доходит до конца. После сборки в runtime оба приложения потребляют заметно меньше, так что эксплуатация без swap возможна, но оставлять swap включённым полезно на случай будущих обновлений и повторных сборок прямо на сервере.

Обновление и резервное копирование: код и контент обновляются по принятой в колледже процедуре; база данных Strapi и загруженные медиафайлы при необходимости резервируются на отдельный носитель или в хранилище хостинга.
